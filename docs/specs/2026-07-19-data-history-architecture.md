# 数据与历史版本架构

## 目标

第三优先级收敛数据边界和工作区复杂度，同时让已有 `content_versions` 从后台留档变成用户可恢复的能力。

## 数据边界

- SQLite 原生 SQL 是唯一 schema 来源，建表与兼容迁移集中在 `src/lib/novel-db/initialize.ts`。
- repository 是唯一持久化入口，负责事务、snake_case 到 camelCase 映射和版本留档。
- server action 使用 Zod 校验输入，向组件返回可判别的成功或失败结果。
- 页面和组件使用 `src/modules/novels/types.ts` 的 DTO，不依赖数据库行或 ORM 表定义。

## 版本策略

正式保存且内容确实变化时，保存前内容写入 `content_versions`。覆盖范围包括：

- 六步结果；
- 最终选题和本卷大纲；
- 十章剧情单元、十章分章大纲；
- 章节正文；
- 本书专用创作要求。

恢复历史版本复用正常保存路径，因此恢复前的当前内容会形成新历史，可继续撤销。草稿自动保存不制造历史噪声，单纯切换章节发布状态也不制造内容版本。

## 备份兼容

JSON 格式继续使用 `version: 1`，新增的 `contentVersions` 是可选字段，缺失时解析为 `[]`。因此旧备份可继续导入，新备份导入为新小说时会重建历史记录并替换所属小说 ID。

## 组件边界

`novel-workspace.tsx` 保留跨面板编辑状态和业务编排；工作流侧栏、Codex 状态面板、历史版本列表独立为展示组件，避免继续把所有交互标记堆入单文件。
